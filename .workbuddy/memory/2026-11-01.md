## 全景720（iPhone 球面全景相机）— 从零构建并出包

工作目录：`D:/ai produe/720`，仓库：https://github.com/gfhghj312-cyber/pano720-ios （public，免费 Actions 额度）

### 技术决策（重要，后续改动要遵守）
- **纯姿态拼接，不用 OpenCV/特征点**：每帧记录 CoreMotion `attitude`（`.xArbitraryZVertical`，Z 轴垂直），
  等距圆柱图逐像素求世界射线 → `c = Rᵀ·w` → 针孔投影 → 边缘羽化 + cos³ 权重混合 + 亮度增益。
  Metal compute shader 以字符串运行时编译（`device.makeLibrary(source:)`），避免 .metal 文件与工程配置。
- **采集用 AVCaptureVideoDataOutput 而非 PhotoOutput**：缓冲区朝向确定（`videoRotationAngle = 90`，
  竖屏锁定），无 EXIF 歧义；镜头内参 `focal = (longEdge/2)/tan(hFOV/2)`，`tanHalf` 是比例所以缩放不变。
- **格式选择**：优先 4:3 且 longEdge ≤ 2400（12MP 视频流会掉帧），2.5s 无出图自动降档到 ≤2000。
- 纹理用 `texture2d_array` 单次绑定（避开 31 个纹理参数上限），源图按张数动态降采样，显存约 140MB。
- 工程用 XcodeGen（`project.yml`），`.xcodeproj` 已 gitignore，CI 里生成。

  拷 `.app` 到 `Payload/` → zip 改名 `.ipa`。产物 arm64、无 `_CodeSignature`，可用自签工具签名。

### UI
- iOS 26+ 用原生 `.glassEffect(.regular, in: shape)`，用 `#if compiler(>=6.2)` + `#available(iOS 26.0)` 双重保护，
  低版本回退 `ultraThinMaterial + 高光描边`（封装在 `Sources/Support/Theme.swift` 的 `GlassSurface`）。

## 第二轮：拼接全糊 + 空洞 的根因修复（2026-11-01 深夜）

### 根因（两个都是硬 bug）
1. **旋转矩阵传反**：`StitchService` 传给 Metal 的是 `R` 的行，着色器算 `c = R·w`；
   正确应为 `Rᵀ`（世界→相机）。准星视图 `AlignmentReticle` 用的是 `rotation.transpose`，
   两处矛盾 —— 准星是对的，拼接是错的。这直接导致每帧落到错误球面位置、37% 空洞。
2. **机位网格经度步长公式低估**：`stepYaw = 2·asin(sin(stepH/2)/cosP)` 在高纬度严重偏小，
   环与环之间必然留缝。

### 修复要点
- `simd_float3x3.worldToCameraRows4`（传列 = Rᵀ 的行）；着色器注释写明相机沿 -Z。
- `CMAttitude` 旋转方向**运行时用重力判定**（参考系重力恒为 (0,0,-1)，
  与 `deviceMotion.gravity` 比两种解释的误差），不再依赖文档猜测；判定结果统一成「相机→世界」。
  ⚠️ Apple WWDC 与 SO 上的说法互相矛盾，别凭记忆写死方向。
- 机位网格改为**贪心球面覆盖**：5200 个 Fibonacci 采样点，视场矩形（按 overlap 收缩）精确判定覆盖，
  每次在「离所有已有机位最远的未覆盖点」放新机位。极点 (|z|>0.93) 改用旋转不变的圆判定
  （举手机对天顶时滚转角不确定）。
- 姿态按**视频帧 PTS** 在历史里四元数 slerp 取（补偿视频流 1~2 帧延迟）；时间轴不同源时退回当前姿态。
- 超广角：开 `isGeometricDistortionCorrectionEnabled`，读 `geometricDistortionCorrectedVideoFieldOfView`，
  中央 `crop=0.92` 参与拼接。
- 拼接第二轮：未覆盖像素放宽边界 45% + 钳制采样做边缘外推，杜绝黑块。
- `setBytes` 有 4KB 上限 → 参数表改用 `MTLBuffer`。

### 参数（仿真定标）
`overlap=0.16` → 1× 约 35 张，0.5× 约 14 张；`feather=0.11`(ext.w)。

### 验证方法（重要，可复用）
`Tools/verify_stitch.py`：合成全景 → 按机位 pinhole 反投影出帧 → 用与 MSL 逐字对应的公式拼回 → 比真值。
结论：正确 Rᵀ = 0% 空洞 / PSNR 31.4dB（误差均匀，只有极区 1~2 行拉伸）；
传 R = 37% 空洞 / 7.9dB。±0.7° 姿态抖动下 PSNR 几乎不变。
**以后动投影数学必须先跑这个脚本。**

## 第三轮：1x 切换失效 + 接缝重影（2026-11-02）

### 用户反馈
「只能用广角，点 1x 没反应」「拍出来有重影」。看用户给的成品图：门框、顶角石膏线
在重叠区出现明显双线（半透明重影），接缝处竖直补偿 0 像素、列差仅 1.23x
→ 说明**不是接缝这一处的问题，而是每一对帧都轻微错位**（陀螺仪偏航随拍摄累积漂移）。

### 根因
1. **重影 = 陀螺仪漂移**。整圈几十秒，yaw 漂 1~3°；羽毛化混合把两帧的同一根边
   各画一遍 → 半透明双线。旧代码只靠姿态，没有任何残差修正。
2. **1x 切换**：`applyLensLocked` 在运行中的会话里换 input，且 `applyBestFormat`
   在 `commitConfiguration` 之前设 activeFormat —— `.photo` 预设会在 commit 时把它重置。
   换输入在任何一步失败都不会恢复，也没有任何用户可见反馈。

### 关键坑（务必记住）
- 做光度配准时，**样本必须撒在重叠区里**。整幅撒点、靠 mask 过滤，重叠只有 15% 时
  256 点里剩三十来个，角度估计噪声 0.3~0.5°，精配准精度全被这个限死。
- **必须用图像金字塔**。0.8° 以上单尺度直接掉进局部极小值（场景里直边/条纹会误匹配）。
- **成对解收敛后残差梯度≈0**，拿它装配全局法方程会得到 0 修正。要用「δi−δj=d」这种
  *相对约束*线性装配，而不是 Hp/bp。
- 验证精配准时**不能看 PSNR vs 真值**：整体旋转是规范自由度，会把结论带偏。
  正确判据是**重叠区一致度**（同一处被两帧看到时的 RMS），规范无关，直接对应用户看到的鬼影。

### 验证结果（Tools/verify_align.py）
1x：姿态误差 1.03°→0.65°，重叠一致度 16.67→8.76（理想 4.00），重影降 47%
0.5x：1.06°→0.33°，16.49→10.84，降 34%
单对收敛范围：注入 0.3/0.8/1.5/2.5° 都能解回 ±0.01°（加金字塔之后）。

### 改动
- 新增 `Stitch/FrameAligner.swift`（金字塔光度 GN + 3N×3N 旋转平均 + 逐帧增益解）
- `StitchService` 整体挪到后台线程（原来在主线程卡住，进度条不动）
- 羽化 0.11→0.07 且平方，过渡带变窄
- `CameraController`：`sessionPreset = .inputPriority`；切换先 stopRunning、commit 后再设
  activeFormat；1.6s 出图看门狗 + 失败回滚；`waitForFreshFrame`
- 默认镜头改 1×（角分辨率高 2.4 倍）
- 结果页显示「对齐残差」（0.2~0.5° 正常，>1° 说明拍太快或太暗）

## 第四轮："还是不行拼接得很烂"（2026-11-02 下午）

### 本轮找到的根因：内参没有按真实缓冲区尺寸算
Apple 文档（videoRotationAngle）原文：「设定角度**并不总是**旋转像素……与 AVCaptureVideoDataOutput
的连接会提供经过物理旋转的缓冲区」。关键：`isVideoRotationAngleSupported` 返回 true
**不代表设置会生效**（有实测：前置摄像头静默忽略，buffer 仍是横向）。

旧代码 `configureIntrinsics` 无条件按「竖屏」分配：
`tanHalfH = shortEdge/2/focal`, `tanHalfV = longEdge/2/focal`。
一旦系统没旋转（buffer 横向 1920×1440），宽高正好颠倒 →
水平被压扁、垂直被高估 → 接缝重影 + 环间空洞。

**为什么仿真从没发现**：verify_stitch.py 的帧是用标准针孔模型直接生成的，
不存在「相机 pipeline 旋转」这一层，所以永远自洽。

仿真量化（1x, 640×320）：
| 内参 | 有效区平均误差 | PSNR |
| 正确 0.487/0.650 | 5.5 | 29.7dB |
| 宽高颠倒 | **28.0** | **17.0dB** |
| 整体偏 10% | 20.4 | ~20dB |
→ 内参精度是决定性的，10% 偏差就让误差翻 4 倍。

### 改动
- `intrinsicsFor(size:device:)`：用 `max(w,h)` 定位传感器长边（videoFieldOfView 描述的
  就是长边方向），再按宽高比分配 tanH/tanV。横竖两种情况都自洽。
  畸变校正开启时用 `geometricDistortionCorrectedVideoFieldOfView`。
- 首帧到达时用实际 CVPixelBuffer 尺寸重算，回调 `onIntrinsicsChange` 让上层重建机位网格。
- `encodeJPEG`：缓冲区横向则 `CIImage.oriented(.right)` 主动旋成竖屏，
  保证 u→右 / v→下 的约定成立。
- 换镜头时清 `lastBufferSize`（同尺寸但 FOV 变了，否则不重算）。
- **精配准安全阀**：`FrameAligner.ghostScore`（规范无关的重叠一致度）前后对比，
  没有 <0.97× 就不采用，退回纯陀螺仪。`residualDeg = -1` 表示被拒。
- **MotionService 旋转方向判定改多帧投票（20 票）后锁定**。中途翻转会让 history 里
  四元数混两种解释，slerp 出垃圾 —— 比判错更隐蔽。
- 拍摄不足（<85% 机位）时拦截拼接并说明原因。之前 2 张就能拼，必然烂。

### 下一步若仍失败：用结果页「对齐残差」那行分流
- 显示「精配准未通过校验」→ 几何有系统性错误（内参/姿态），要继续查几何
- 显示「对齐残差 0.x°」→ 配准生效但结果仍差 → 看是否拍太少 / 视差 / 走位

## 第五轮：换成 OpenCV 特征引擎 + 两频段融合（2026-11-02 傍晚）

### 用户反馈
"还是很糟糕有没有什么现成的引擎可以套进去的" —— 自研拼接连续 4 轮不达标，
这次不再调参，直接把姿态估计换成成熟前端。

### 采用了什么
**OpenCV 5.0.0 官方 iOS 静态框架**（44MB zip，解压 149MB，arm64 设备 + x86_64 模拟器）。
只用来算「两帧之间的相对旋转」，球面投影和融合仍自己控制（输出严格 2:1 等距圆柱）。

- `PanoCVMatcher.mm`（ObjC++）：SIFT（弱纹理退回 ORB）+ KNN 比值筛选 + RANSAC 单应，
  由 `R = S·(K⁻¹HK)·S`（S = diag(1,-1,-1)）换回本工程相机约定
- `FeatureAligner.swift`：每帧最多 4 个最近邻 → 3N×3N 旋转平均 → 逐帧增益
- `composeBands` 着色器：宽羽化低频 + 窄羽化高频，三趟渲染合成

### 踩过的坑（务必记住）
1. **OpenCV 5 模块改名**：`features2d`→`features`，`calib3d` 拆成 `calib`/`geometry`，
   `findHomography` + `RANSAC` 在 `geometry/3d.hpp`（由 `geometry.hpp` 聚合）。
   **AKAZE 在 5.0 里已被移除**，`cv::AKAZE` 直接编译失败。用 SIFT/ORB。
2. **框架是静态 fat 库**，`embed: false` 即可，签名时不用管嵌套 framework。
   CI 里必须用 `ditto -x -k` 解压，`unzip` 会破坏 versioned bundle 的符号链接。
3. **旋转平均必须加 Levenberg 阻尼**。环状机位图的结构矩阵有一类
   「整体缓慢旋转」的弱约束方向，接近奇异；λ=1e-3 时步长逐轮指数放大
   （3.6→2.3→2.6→3.1→4.1→5.4→7.2°），3 轮后整圈飞出 23°，比不用还差。
   λ=0.6 + 12 轮：相对姿态误差 0.77°→0.57° / 0.67°→0.43°。
   固化在 `Tools/verify_rotation_averaging.py`（含发散对照组）。
4. **CGImage → cv::Mat 要翻转 CTM**（CGBitmapContext 原点在左下），
   否则像素 y 轴与 `tanHalfV` 的映射相反，解出的 R 会整体多一个绕 X 的 180°。
   单应→旋转的符号约定用 Python 验过：`R_ours = S·(K⁻¹HK)·S`，误差 1.9e-16。
5. `photometricAlign(progress:)` 需要 `@escaping`（传给 FrameAligner.refine 的可选闭包）。

### 尺寸
二进制 1.5MB → 6.82MB，IPA 2.9MB。可接受。

### 若仍然不达标，下一步
应导出真机原始帧 + 姿态做离线复现（而不是继续猜）。
